WebP 在前端项目中的使用实践 ​

原文地址

WebP 在前端项目中的使用实践 | GitHub

图片基本是前端页面中体积占比最大的资源类型，而 WebP 是目前前端最值得优先使用的一种图片格式。
这篇文章从日常工程使用的角度，整理一下 WebP 的定位、适合的使用场景、常见接入方式，以及一些实际踩过的坑。

一、WebP 是什么？ ​

WebP 是 Google 推出的图片格式，本质目标只有一个：
在尽量保证视觉质量的前提下，缩小图片体积。

它同时支持：

  • 有损压缩（类似 JPG）
  • 无损压缩（类似 PNG）
  • 透明通道
  • 动画（类似 GIF）

这也是 WebP 最大的特点：
一个格式基本覆盖了 JPG、PNG、GIF 三类图片的核心使用场景。

二、和常见图片格式的区别 ​

从前端最关心的几个点简单对比一下：

维度JPGPNGGIFWebP
有损压缩✅❌✅✅ / ❌
透明❌✅✅✅
动画❌❌✅✅
文件体积小大很大最小
常见用途照片透明图动图通用替代

在实际项目中，一个比较直观的结论是：

只要业务不强依赖极老浏览器，大多数图片都可以优先使用 WebP。

三、为什么前端项目值得优先用 WebP？ ​

1. 体积优势非常明显 ​

实际项目中常见的体积差距：

  • WebP 比 JPG 小 25% ~ 60%
  • WebP 比 PNG 小 50% ~ 80%
  • 动画 WebP 比 GIF 通常小 80% 以上

这些差值直接影响：

  • 页面整体体积
  • 首屏加载速度
  • 移动端流量消耗
  • CDN 带宽成本

而且这是“换格式就能拿到的收益”，不涉及业务逻辑改造。

2. 使用方式更统一 ​

过去我们一般是：

  • 照片 → JPG
  • 透明图 → PNG
  • 动画 → GIF

在支持 WebP 的项目中可以简化成：

  • 默认 WebP
  • 必要时回退 JPG / PNG

对资源管理反而更友好。

3. 浏览器兼容性已不是主要阻力 ​

目前主流环境（Chrome、Edge、Firefox、Safari 新版本、Android、iOS）都已支持 WebP。
真正需要担心的主要是一些：

  • 老旧 Android WebView
  • 很老版本的 iOS 浏览器
  • 极个别内嵌浏览器

所以现在的普遍做法是：
不是“只用 WebP”，而是“WebP + 兜底”。

四、哪些前端场景最适合用 WebP？ ​

比较典型、收益也最明显的场景有：

  • 商品主图、商品详情图
  • 运营 Banner、首页大图
  • 移动端 H5 图片
  • 透明 UI 装饰图（替代 PNG）
  • 动画图片（替代 GIF）

不太适合的场景：

  • 图标系统：SVG 更合适
  • 对极老浏览器有强要求的系统：仍以 JPG / PNG 为主

五、前端最常见的 WebP 使用方式 ​

1. 使用 <picture> 做格式兜底（推荐） ​

这是目前最稳妥、兼容性也最好的写法：

html
<picture>
  <source srcset="image.webp" type="image/webp">
  <img src="image.jpg" alt="demo">
</picture>
1
2
3
4

浏览器行为是：

  • 支持 WebP → 自动加载 .webp
  • 不支持 WebP → 回退加载 .jpg

前端不需要额外写 JS 判断逻辑。

2. 透明图从 PNG 迁移到 WebP ​

html
<picture>
  <source srcset="btn.webp" type="image/webp">
  <img src="btn.png">
</picture>
1
2
3
4

这类 PNG 在很多项目中体积都偏大，迁移到 WebP 之后优化效果通常很直观。

3. 动画从 GIF 迁移到 WebP ​

原来：

html
<img src="loading.gif">
1

可以直接改成：

html
<img src="loading.webp">
1

在多数业务场景下无需额外处理，文件体积却能小很多。

六、从性能角度看 WebP 的实际价值 ​

WebP 对性能的影响非常直接，主要体现在：

  • 页面资源总大小
  • 首屏 LCP
  • 移动端弱网加载体验
  • 带宽和流量成本

在不少项目中，仅通过把主要 JPG / PNG 资源切换为 WebP，就能明显改善首屏加载时间，而且改造成本很低，属于 “优先级很高的基础优化项”。

七、一些实际使用中的注意点 ​

  • 一定要有兜底
  • 不建议只给 .webp
  • 使用 <picture> 或 CDN 自动协商
  • 设计工具直接导出的 WebP 不建议直接上线
  • 不同工具压缩策略差异较大
  • 建议统一在构建阶段或 CDN 层处理
  • 少量透明图片可能存在边缘色差
  • 尤其是 UI 组件类图片
  • 上线前建议重点图片做一次肉眼验收

八、CDN 按 Accept 头自动转 WebP（前端零改造方案） ​

这是目前很多中大型项目使用的方案：
前端仍然引用原始 JPG / PNG，是否返回 WebP 由 CDN 自动判断。

1. 浏览器请求头示例 ​

现代浏览器在请求图片时通常会携带：

arduino
Accept: image/avif,image/webp,image/*,*/*
1

这表示浏览器支持 WebP / AVIF，优先接收这些格式。

2. CDN 的处理逻辑 ​

text
浏览器请求：example.com/banner.jpg
        ↓
CDN 读取 Accept 头
        ↓
支持 WebP → 返回 banner.webp
不支持 WebP → 返回 banner.jpg
1
2
3
4
5
6

前端代码保持不变：

html
<img src="https://cdn.xxx.com/banner.jpg">
1

但支持 WebP 的浏览器实际拿到的是 .webp 资源。

3. 常见支持该能力的 CDN ​

  • 阿里云 OSS + CDN 图片处理
  • 腾讯云 COS + 数据万象
  • 七牛云
  • Cloudflare
  • AWS CloudFront（配合 Image Handler 或函数）

常规配置步骤：

  • 开启图片处理服务
  • 开启 WebP / AVIF 自动转换
  • 按 Accept 头维度区分缓存

4. 这种方案的优缺点 ​

优点：

  • 前端零改造
  • 老项目也可以平滑接入
  • 不需要维护 WebP 资源
  • 可随时关闭

缺点：

  • 依赖 CDN 能力
  • 本地环境无法完全模拟线上效果
  • 可能产生额外转码费用

九、构建阶段自动生成 WebP（补充方案） ​

如果不依赖 CDN，也可以在构建阶段生成 WebP：

常见工具：

  • vite-plugin-imagemin
  • image-webpack-loader
  • sharp

构建产物示例：

text
logo.png    → logo.webp + logo.png
banner.jpg → banner.webp + banner.jpg
1
2

再配合 <picture> 使用即可。

十、WebP 在项目中的使用原则总结 ​

text
1. 照片类图片：优先 WebP，JPG 兜底
2. 透明图片：优先 WebP，PNG 兜底
3. 动画图片：优先 WebP，GIF 兜底
4. 图标类：优先 SVG
5. 老旧环境：回退 JPG / PNG
6. 老项目改造：优先考虑 CDN 自动 WebP
