【前端必修】后端返回超出 JS 最大安全整数的大数字，纯前端如何保证不丢精度？ ​

原文地址

超出 JS 最大安全整数的大数字，纯前端如何保证不丢精度？ | GitHub

场景：后端接口返回 Long / BigInt 类型的大整数（如订单号、ID、金额分），
前端使用 JavaScript 接收后 自动丢失精度，导致数据错误、对账失败、线上事故。

本文将系统讲清：

  • ❓ 为什么前端一定会丢精度
  • ✅ 纯前端在不能改后端的情况下如何彻底解决
  • ✅ axios / fetch 的工程级接入方案
  • ⚠️ BigInt 的正确使用姿势
  • ✅ 公司级最佳实践总结

一、问题本质：JS 的最大安全整数限制 ​

JavaScript 中所有数字默认都是 Number 类型，基于 IEEE 754 双精度浮点数：

js
Number.MAX_SAFE_INTEGER === 9007199254740991
1

只要后端返回的整数超过这个值，前端在 JSON.parse 阶段就会丢失精度，且不可逆。

示例 ​

后端返回： ​

json
{ "id": 9223372036854775807 }
1

前端真实拿到的值 ​

js
9223372036854776000 // ❌ 精度已丢
1

⚠️ 注意：
这个错误不是出现在页面展示，而是在 浏览器解析 JSON 时就已经发生，后面任何补救都无效。

二、纯前端可行的 4 种解决方案对比 ​

在不能修改后端返回格式的前提下，前端只有以下几种路可走：

方案推荐指数是否引入库是否支持计算适用场景
json-bigint（storeAsString）⭐⭐⭐⭐⭐✅❌（仅展示）订单号 / 流水号 / ID（展示优先）
json-bigint（useNativeBigInt）⭐⭐⭐⭐✅✅需要做大数运算（财务 / 计量）
手写正则替换字符串⭐⭐❌❌严格受控、短期应急
全部当字符串展示⭐⭐⭐❌❌展示为主、无需计算

✅ 实际生产强烈推荐：json-bigint

三、最稳妥方案：使用 json-bigint（企业级标准解法） ​

1️⃣ 安装 ​

js
npm install json-bigint
1

2️⃣ 展示型场景（最推荐配置：转字符串） ​

适用于：

  • 订单号
  • 流水号
  • 业务主键
  • 只展示、不参与运算的大数字
js
import axios from 'axios'
import JSONBig from 'json-bigint'

const JSONBigSafe = JSONBig({
  storeAsString: true
})

axios.defaults.transformResponse = [function (data) {
  return JSONBigSafe.parse(data)
}]

四、不引入第三方库的兜底方案（不推荐，只适合应急） ​

如果你所在的项目 严格禁止安装依赖，可以使用正则强制把超长数字转为字符串：

js
function safeJsonParse(str) {
  return JSON.parse(
    str.replace(/:\s*(\d{16,})/g, ': "$1"')
  )
}

❌ 可维护性较差，不建议长期使用

五、BigInt 的正确使用规范（否则会踩坑） ​

✅ 1. 运算必须同类型

js
10n + 20n   // ✅
10n + 20    // ❌ 会直接抛异常
1
2

✅ 2. BigInt 不能直接 JSON.stringify

错误示例：

js
JSON.stringify({ id: 10n })
// ❌ TypeError: Do not know how to serialize a BigInt
1
2

正确写法：

js
JSON.stringify(obj, (_, v) =>
  typeof v === 'bigint' ? v.toString() : v
)

✅ 3. Vue / React 渲染 BigInt 建议转字符串

七、哪些字段必须重点防丢精度？ ​

✅ 真实项目中，以下字段 必须默认按“不可信 Number”处理：

  • 数据库主键（Long / BigInt）
  • 订单号 / 流水号
  • 财务金额（分）
  • 区块链交易号
  • 雪花 ID（Snowflake）

八、最常见的 5 个致命误区 ​

错误做法后果
直接 JSON.parse第一时间丢精度
丢精度后再转字符串永远无法恢复
BigInt + Number 运算程序直接崩溃
BigInt 直接 stringify直接抛异常
信任后端一定不会超限线上必出事故

九、公司级“终极推荐方案”与规范 ​

在不能改后端的情况下，建议把这套方案写入 团队技术规范：

  1. 所有前端接口响应统一用 json-bigint 在接入层解析（storeAsString = true）
  2. 所有后端返回可能超 15 位的字段，在前端一律按字符串处理
  3. 只有在确实需要数值运算的场景，明确将字符串转 BigInt（并在边界处注释）
  4. 禁止在业务代码中直接使用 Number 去解析数据库主键 / 订单号等超大整数
  5. 增加 ESLint 规则或 PR 检查，用静态分析防止误用

对应实现（示例）：

js
// api/parse.js
import JSONBig from 'json-bigint'
export const parseJsonSafe = JSONBig({ storeAsString: true }).parse

2
3

在项目中统一引入 parseJsonSafe 做响应解析，避免零散处理导致遗漏。

十、一句话总结（可写入团队技术规范） ​

任何来自后端、长度超过 15 位的整数，前端禁止使用 Number 直接接收，必须通过 json-bigint 或字符串化进行安全解析，否则必然发生精度错误。

十一、结语 ​

前端大数字精度问题：

  • ❌ 不是“偶发 bug”
  • ❌ 不是“某个浏览器的问题”
  • ✅ 而是 JavaScript 数值模型的先天限制
  • ✅ 必须通过“工程化方案”统一解决

如果你所在团队至今仍在直接 JSON.parse 接收 Long 型数据，
那不是“如果会出问题”，而是“只是还没出问题”。

推荐：
统一用 json-bigint（storeAsString） 解析；必须运算时再明确转 BigInt。

可扩展项：

  • Vue / React 插件封装（拦截器 + 类型转换）
  • ESLint 规则防误用 Number
